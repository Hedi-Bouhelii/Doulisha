# 0002. Neon PostgreSQL and Drizzle instead of Supabase

- Status: Accepted
- Date: 2026-09-23

## Context

Specification section 9 recommends Supabase (Postgres, auth, storage and realtime) for the MVP. The build prompt (`docs/BUILD_PROMPT.md`) wins on technology choices. It mandates:

- Neon and Drizzle for the database;
- Better Auth;
- Cloudflare R2 for storage;
- polling instead of realtime.

It also forbids Supabase and Firebase Auth.

## Decision

- **Database:** Neon serverless PostgreSQL through `@neondatabase/serverless`:
  - the HTTP driver for simple queries;
  - the WebSocket `Pool` for transactions (bookings, payments, ticket stock with `SELECT … FOR UPDATE`).
- **ORM:** Drizzle ORM, with SQL migrations generated by drizzle-kit and committed. `drizzle-kit push` is never used against production.
- **Extensions:** `postgis`, `pg_trgm` and `unaccent`, enabled in the first migration (Phase 1).
- **Branching:** one Neon branch per pull request and preview deployment, seeded with data.
- **Replacements for Supabase features:**
  - auth: Better Auth (ADR 0003);
  - storage: Cloudflare R2;
  - realtime: TanStack Query polling in the MVP, then Ably or Pusher behind an interface for chat in V1.

## Consequences

- **Portability:** everything is standard Postgres, with no vendor-specific row-level security or auth schema.
- **More code to own:** permissions live in our services, and we sign uploads ourselves.
- **Realtime becomes polling:** the spec's "realtime covers feed, chat and live counters" is replaced by polling in the MVP.
  - The "18/25 places" counter can lag by a few seconds.
  - Overselling is still impossible, because the database locks stock rows.
